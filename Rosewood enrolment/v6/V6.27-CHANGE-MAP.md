# V6.27 Application-Link Delivery Status Change Map

## Release Boundary

- Current EOI: `rosewood-eoi-2026.26`
- Current Application: `rosewood-application-2026.27`
- Public request contract: unchanged at `rosewood-application-link-request-2026.1`
- Family questions, answers, validators, invitations, submissions, uploads and
  signatures: unchanged

## Problem

Public request records retain `status: invitation_queued` because the authoritative
transaction created durable email work. The staff portal previously displayed that raw
value indefinitely as **Invitation queued**, even after SES accepted or delivered the
message. That mixed business-request state with transport state and could lead staff to
create an unnecessary replacement invitation.

## Projection

The stored request remains unchanged. The authenticated dashboard now derives:

| Portal field | Authoritative source | Display |
| --- | --- | --- |
| Request | Application-link request `outcome` and `requestedAt` | Application link requested / requested again |
| Application relationship | Request `outcome`, `invitationId` and `applicationId` | New application created / Existing application retained |
| Queued | Current `OUTBOX` item for the exact request ID | Email queued |
| Sent | Completed email outbox receipt | Email sent |
| Delivered/delayed/failure | Latest SES configuration-set event for the exact request ID | Email delivered / delayed / failed / complaint received |
| No retained evidence | No matching current outbox, receipt or SES event | Delivery status unavailable |

When evidence timestamps tie, the more conclusive state wins. A later SES delivery or
failure supersedes SES acceptance. The transport projection cannot mutate the request,
invitation or Application.

## Privacy And Retention

The current pending/failed outbox query uses a DynamoDB projection containing only email
kind, event time and `workflow`, `message_type` and `record_id` tags. It does not project
the recipient, subject, text, HTML or provider message ID. The staff response continues
to expose the already-authorised request email, but never adds an SES identifier.

Completed outbox receipts are temporary and SES feedback is retained for a bounded
period. Therefore **Delivery status unavailable** is the truthful state for some older
requests. It must never be translated back to queued or treated as proof of failure.

## Interface

- Desktop cards show request, Application relationship, email status and latest evidence
  time separately.
- Mobile cards keep family identity, current email status, evidence time and the existing
  Application action without horizontal scrolling.
- Each status badge is keyboard focusable and has a screen-reader description. The
  delivered description says the recipient mail server accepted the message and that it
  may still be in junk.
- No request-list resend or mutation action was added.

## Verification

Automated coverage includes queued, SES-accepted, delivered, delayed, bounced, terminal
outbox failure, unrelated email type and expired/unavailable evidence. It also verifies
exact request-ID correlation, omission of provider IDs, privacy-limited DynamoDB
projection, accessible status descriptions and responsive styling. Production release
evidence is recorded in `TESTING.md`.
