# Rosewood Enrolment V6.7 Change Map

## Release Boundary

V6.7 changes the live EOI/Application frontend assets and the Application question
contract. EOI storage fields are unchanged. Application, EOI, offer acceptance,
Enrolment Agreement and decline remain separate workflows and records. Acceptance and
decline remain non-writing previews.

Submitted applications are immutable. New invitations use V6.7. Editable applications
created by earlier invitations upgrade to V6.7 on their next verified open. The upgrade
preserves existing answers, increments the application revision, records the old/new
definition in restricted audit history and never creates a duplicate application.

## Interface Map

| Requested area | V6.7 result |
| --- | --- |
| Mobile child selector | Replaced wide table behavior with icon-led cards showing student, source, status and action without horizontal scrolling |
| Rosewood entry | Labels explicitly identify the year and year level at Rosewood; 2027 is first/default |
| Countries and languages | Native searchable datalists; 249 ISO-region entries plus Kosovo and the existing 444-entry ASCL catalogue |
| Addresses | Privacy-preserving browser address autofill tokens for student, guardian and postal addresses; no unapproved Google/third-party address request or API key |
| Add Contact | Primary action styling, short legal-guardian reminder, and focus/scroll to the newly created contact card |
| Mobile dates | Full-width constrained controls; future sacrament dates blocked in browser and backend |
| Sessions | Same-tab opaque-token restoration while active; blocking expiry flow remains after 20 minutes inactivity |
| Staff access | Optional Remember me with backend-enforced two-hour sliding expiry and explicit logout/expiry clearing |
| Signer review | Internal application revision labels are removed from family-facing text |

Browser address autofill depends on addresses saved in the family's browser/device. A
Google Places-style network search was not enabled because no approved API key,
provider agreement, privacy assessment or data-routing decision exists. This avoids
silently disclosing typed family addresses to a new third party. Adding external
address search later requires a separate approved release.

## Data Contract Changes

Added keys:

- `previous_school_attended`, `previous_school_year_level`
- `interrupted_schooling`, `interrupted_schooling_details`
- `formal_assessment`, `formal_assessment_details`, `formal_assessment_report`
- `current_adjustments`, `rosewood_adjustments`
- `medicare_reference`
- `private_insurance_provider`, `private_insurance_policy`
- `student_healthcare_number`, `student_healthcare_expiry`
- `application_student_agreement`, `application_parent_agreement`
- `application_agreement_acknowledgement`

No longer visible or required for V6.7:

- `previous_school_permission`, previous-school address/interstate questions
- all `fee_*` questions
- application discovery and three-influence survey questions

Retired answers already saved are preserved in DynamoDB revisions and are not silently
deleted. They are not carried into the new visible Conditions projection as current
consent. Google Sheets remains an append-compatible reporting projection, not the
authority.

## Validation And Submission

- Previous institution/year level are required only after previous attendance Yes.
- Interrupted-schooling details are required only after Yes.
- Formal-assessment details and report availability are required only after Yes.
- Student Health Care Card number/expiry are required only after Yes.
- Guardian marital status and religion, doctor phone, Medicare number and Medicare Ref
  Number are required; guardian/student ethnicity remains optional as specified.
- The three V6.7 agreement acknowledgements are required.
- The Lambda computes the signing date in `Australia/Melbourne` at successful
  submission and overwrites any browser-supplied date before validation, hashing,
  snapshot creation and signature evidence.

## Post-Offer Boundary

Previous-school contact permission has moved out of Application. The future post-offer
Enrolment Agreement/onboarding workflow must ask for it explicitly after an offer is
accepted. Supplying a prior institution name is not consent to contact it.

## Compatibility And Recovery

- The frontend can render form versions `2026.1` through `2026.7`.
- Current editable records are upgraded transactionally; submitted records are not.
- Draft saves continue to merge visible answers and preserve omitted/retired values.
- Existing invitation tokens, OTP controls, upload records and application identifiers
  are unchanged.
- The outbox updates Sheets after an upgrade; operators rebuild projections from
  DynamoDB if needed and never repair by editing Sheets.
- A stale client/form hash fails closed without overwriting the draft.

## Verification Contract

Release verification covers syntax, all backend tests, immutable asset hashes,
deployment build, CloudFormation change review, production health/current versions,
same-tab session restoration, mobile/desktop layout, conditional questions, server
date enforcement, active-draft upgrade and preservation, staff sliding sessions, and
the existing guardian contact/signature security suite. Only synthetic records may be
used for canaries.
