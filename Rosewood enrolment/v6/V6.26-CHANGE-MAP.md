# V6.26 Cohort Planning Change Map

Release date: 2 September 2026

## Immutable Contracts

- Current EOI: `rosewood-eoi-2026.25`
- Current Application: `rosewood-application-2026.26`
- Previous EOI/Application definitions remain addressable and unchanged.
- This release changes no family question, answer key, condition, validator, upload,
  submission, signature, communication or meeting rule.

## Staff Interface

**Enrolment planning** becomes **Cohort planning** with three views:

1. **Applications** preserves the existing application planning list, filters and
   review action.
2. **Prospective families** maintains staff-only planning records with explicit contact
   permission, status, source, follow-up and one or more child cohorts.
3. **Combined forecast** counts family Applications and unlinked active prospective
   children by intended year and entry level.

The interface is responsive and keyboard-accessible. `viewer` accounts can read but
cannot add, edit, archive or link a prospect. The new `planning_editor` code role can
maintain prospects but is not assigned to any mailbox by this release.

## Storage And Safety

- `prospect_family` and `prospect_child` are separate authoritative DynamoDB entities.
- `prospect_email_index` is a hashed transactional claim that prevents concurrent
  duplicate active family records without putting the raw email in a database key.
- `prospect_application_link` is a conditional uniqueness claim for deliberate links.
- Every create, update, archive, link and unlink is attributable in restricted audit.
- Prospect records have no Google Sheets projection and create no email, Slack, OTP,
  invitation, Application, revision, document or signature record.
- Application linking is never inferred. A confirmed staff action links one existing
  family Application to one prospective child and can be reversed without changing the
  Application.
- Archive is non-destructive. Archived/not-proceeding prospects and marked test
  Applications are excluded from forecast totals.

## Compatibility And Rollout

Static staff assets are safe to publish before the backend: the existing Applications
view still renders, while the new prospect panels show a scoped unavailable message if
the cohort endpoint is not yet deployed. Deploying the backend first would expose no
public route, but static-first remains the approved sequence for active family forms.

Release verification requires the complete automated suite, desktop/mobile visual
checks, pinned asset hashes, a reviewed in-place Lambda change set, `/v6/health`
contract checks, the five-part non-writing canary and all nine production alarms.
